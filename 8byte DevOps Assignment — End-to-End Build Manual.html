8byte DevOps Assignment — End-to-End Build Manual

A field guide for building, documenting and presenting the assignment yourself. This manual tells you what to build, in what order, which resources and settings matter, which official documentation to read for each piece, and how to justify every decision. It deliberately does not hand you finished code — you write every line, which is exactly what the company is checking for.

0. How to use this manual

Read sections 1–4 fully before touching a keyboard. Then work through the phases (5 → 10) in order; each phase ends with a "Done when" checklist so you know you can move on. Keep two files open from the very first minute:

  1. CHALLENGES.md (scratch log) — every time something breaks, write down: what you tried, the error message, the root cause, and the fix. This becomes your Challenges PDF/Word document at the end with almost no extra effort, and it is genuinely the most convincing evidence of original work.
  2. A notes file of "decisions" — every time you choose X over Y (ECS vs EKS, one NAT vs two), write one sentence on why. This becomes the "Architecture decisions" section of your README.

Commit small and often with meaningful messages (feat(network): add private subnets and NAT gateway, fix(ecs): use ip target type for Fargate). A realistic git history with mistakes and fixes is one of the strongest signals of genuine authorship. Don't squash everything into one giant commit at the end.

Happy path first. The PDF says it explicitly. Get one working environment end-to-end (code → image → staging running behind the load balancer) before adding polish. Polish items are marked [Extra] throughout this manual.

2. Architecture decision

2.1 Recommended architecture (happy path)

                         Internet
                            │
                     ┌──────▼──────┐
                     │     ALB     │  public subnets (2 AZs)      ──► access logs → S3
                     └──────┬──────┘
                            │  SG: only ALB → app port
              ┌─────────────▼─────────────┐
              │  ECS Service (Fargate)    │  private-app subnets (2 AZs)
              │  2 tasks, autoscaling     │  ──► stdout logs → CloudWatch Logs
              └─────────────┬─────────────┘
                            │  SG: only App → 5432
                     ┌──────▼──────┐
                     │ RDS Postgres│  private-db subnets (2 AZs)
                     └─────────────┘  ──► postgres logs → CloudWatch Logs

  Outbound from private subnets → NAT Gateway (public subnet) → Internet (ECR, Secrets Manager)

  Supporting: ECR (images) · Secrets Manager (DB credentials) · S3 (TF state + logs)
              CloudWatch (metrics, alarms, dashboards) · SNS (alerts) · IAM OIDC role (GitHub Actions)

Region: ap-south-1 (Mumbai). Justification to write in the README: lowest latency for an India-based team and customers, and 8byte serves BFSI clients — Indian regulators (RBI) have data-localisation expectations for certain financial data, so defaulting to an Indian region is the right instinct. This one sentence shows you read their job description.

2.2 Why ECS Fargate (and how to defend it)

You must be able to defend this choice in R2/R3, especially because the JD emphasises Kubernetes. Your argument:

Option Pros Cons Verdict for this assignment
EC2 + Docker in an ASG Cheapest, full OS control, easy "system logs" You patch the OS, deployments are clunky (instance refresh / SSM), more toil Workable but dated
ECS on Fargate No nodes to manage, native ALB/IAM/Secrets/CloudWatch integration, simple rolling deploys with auto-rollback, small Terraform surface AWS-specific, less control, no host-level logs Chosen — best fit for 9–12 hours and a startup that is "allergic to toil"
EKS Industry standard, portable, rich ecosystem (Helm, Prometheus operator) Control plane cost (~$0.10/hr), node groups, add-ons, IRSA/Pod Identity, ingress controller — easily doubles the effort Mention as the "next step" in README

Phrase it in the README like: "For a single stateless service, ECS Fargate gives production-grade rolling deploys and autoscaling with the smallest operational surface. As the number of services grows, or if portability/Helm-based workflows are needed, I would migrate to EKS; the container image, CI pipeline and RDS/VPC layers would be reused unchanged."

If you are already strong in Kubernetes and want to go EKS, that's legitimate and will impress for this JD — but only if you're confident you can finish everything else in time. Everything in this manual except Section 7.6–7.8 and the deploy step transfers directly. Don't switch mid-way.

2.3 Environments

Two environments, staging and production, each a separate Terraform root with its own state file. They share one ECR repository and one GitHub OIDC role set (in a shared root), because the core CI/CD principle is build once, promote the same image.

Why separate roots instead of terraform workspace: explicit per-env configuration (prod has Multi-AZ, deletion protection, longer backups), smaller blast radius, no risk of applying to the wrong workspace. Write this in your decisions file.

Cost-control note: to save money, production can use the same small sizes as staging during the assignment; the differences (Multi-AZ, deletion protection, retention) are expressed in prod.tfvars and explained. You can even keep prod destroyed except while recording the video.

3. Prerequisites and one-time setup

3.1 Accounts

  • AWS account. Secure it first: MFA on root, never use root again. Create an admin identity for yourself (IAM Identity Center user, or at minimum an IAM user with MFA). Configure the AWS CLI with a named profile.
  • Billing guardrail. Before creating anything, create an AWS Budget with an email alert (e.g. $15/month). Check what free-tier/credits your account has — AWS changed the free tier model for new accounts in 2025, so look at the Billing console rather than assuming.
  • GitHub account and a public repository. Public matters: environment protection rules with required reviewers (your manual approval) are available on public repos on the free plan; on private repos they need a paid plan. They asked you to share the repo anyway.
  • Slack workspace (free) with an Incoming Webhook app installed on a channel such as #deployments. Store the URL only as a GitHub secret.

5. Phase 0 — The application

5.1 Requirements for the app (logic doesn't matter, these properties do)

Whatever you pick, it must have:

  1. An HTTP server listening on a configurable port (env var PORT).
  2. GET /health — liveness, returns 200 without touching the DB. The ALB uses this.
  3. GET /ready [Extra] — checks DB connectivity; useful for smoke tests.
  4. At least one endpoint that reads/writes Postgres (e.g. /api/items list + create). This proves the RDS + secret wiring works in the demo.
  5. Database config read only from environment variables: DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. Never hard-code.
  6. Logs to stdout in JSON, one line per event, including request method, path, status, duration_ms. Structured logs make CloudWatch Logs Insights queries trivial.
  7. A simple frontend (a single HTML page served at / that calls the API is enough — "load balancer for the frontend").
  8. Unit tests that run without a database (mock the DB layer) and integration tests that hit a real Postgres.

5.2 Choosing the app

Two good routes:

  • Write a tiny app yourself (recommended). ~100–150 lines with FastAPI + psycopg or Flask + SQLAlchemy (or Express + pg in Node). It takes ~1 hour, you understand every line, and you can explain it live. Create the table on startup if it doesn't exist (happy path); mention proper migrations (Alembic / a one-off ECS migration task) as [Extra].
  • Use a ready-made project (allowed by the PDF). E.g. a well-known FastAPI/Postgres template or a Node todo app with Postgres. Credit it in the README. Downside: bigger codebases often have heavier builds, more CVEs in scans, and multi-container setups that complicate the ECS task.

Docs to read: FastAPI tutorial (fastapi.tiangolo.com → Tutorial – User Guide, Testing), psycopg 3 docs (Basic module usage), pytest docs (Get started, markers, fixtures). For Node: Express Getting started, node-postgres docs, Jest docs.

5.3 Tests

  • Mark tests so CI can run them separately: e.g. pytest markers unit and integration registered in pytest.ini/pyproject.toml.
  • Unit tests: use the framework's test client (FastAPI TestClient) and override/mock the DB dependency.
  • Integration tests: read DB connection details from env vars; in CI these point to a Postgres service container. Test: create item → list items → item present.
  • Add coverage reporting (pytest-cov) [Extra].

5.4 Dockerfile — what "good" looks like

Write it yourself following these rules (each is a talking point):

  1. Multi-stage build: a builder stage that installs dependencies, a slim runtime stage that copies only what's needed.
  2. Pinned, slim base image (e.g. python:3.12-slim with a specific tag; pinning by digest is [Extra]). Avoid latest.
  3. Dependency layer caching: copy the requirements/lock file and install before copying source.
  4. Non-root user: create a user and switch with USER. Combine later with ECS readonlyRootFilesystem [Extra].
  5. No secrets in the image, .dockerignore excludes .git, tests (optional), .env, __pycache__, node_modules.
  6. EXPOSE the port, run with a production server (uvicorn/gunicorn), exec-form CMD.
  7. HEALTHCHECK is optional — ECS/ALB health checks are what matter on Fargate.

Docs: Docker docs → Building best practices, Multi-stage builds, Dockerfile reference. Run hadolint on it and fix warnings.

5.5 Local run

docker-compose.yml with two services: db (official postgres:16 image, env vars, a healthcheck using pg_isready, a named volume) and app (build from ./app, depends_on with condition: service_healthy, env vars pointing to db). Docs: Docker Compose file reference → depends_on, healthcheck.

Done when: docker compose up works, /health returns 200, you can create and list items, unit and integration tests pass locally, hadolint is clean, first commit pushed.

6. Phase 1 — Terraform foundations

6.1 Conventions to apply everywhere

  • versions.tf: required_version (e.g. >= 1.10) and required_providers pinning hashicorp/aws to the major you install (currently 6.x: ~> 6.0). Many blog posts show v5 syntax — when an argument errors out, check the provider's Version 6 Upgrade Guide. Commit .terraform.lock.hcl.
  • Provider default_tags: Project, Environment, ManagedBy = "terraform", Owner. Every resource gets tagged for free — essential for cost allocation.
  • Naming: a locals { name_prefix = "${var.project}-${var.environment}" } used in every name.
  • Variables: every variable has description and type; add validation blocks where it makes sense (e.g. environment must be staging or production, CIDR must be valid via can(cidrhost(...))). Mark secret-ish values sensitive = true.
  • No hard-coded AZs: use data "aws_availability_zones" and slice().
  • Subnet maths: use cidrsubnet() rather than typing CIDRs.
  • Iteration: prefer for_each (stable keys) over count for subnets/rules.
  • Run terraform fmt -recursive and terraform validate before every commit.

Docs: Terraform Language docs (developer.hashicorp.com/terraform/language) → Variables, Outputs, Locals, Modules, for_each, Functions → cidrsubnet, slice, jsonencode, Backend → s3. AWS provider docs on the Terraform Registry (registry.terraform.io/providers/hashicorp/aws/latest/docs) — this is the single document you'll use most; every resource below has a page with arguments, attributes and examples.

6.2 State management (infra/bootstrap)

The chicken-and-egg problem: the bucket that stores state can't store its own state. Solve it with a tiny bootstrap root that uses local state and is run once.

Resources:

  • aws_s3_bucket — globally unique name, e.g. <project>-tfstate-<account-id>. Add lifecycle { prevent_destroy = true }.
  • aws_s3_bucket_versioning — Enabled (lets you recover a corrupted/overwritten state).
  • aws_s3_bucket_server_side_encryption_configuration — SSE-S3 or SSE-KMS.
  • aws_s3_bucket_public_access_block — all four settings true.
  • [Extra] bucket policy denying non-TLS requests (aws:SecureTransport = false).

Locking: Terraform 1.10 introduced S3 native state locking (use_lockfile = true in the backend); since 1.11 it is the recommended approach and the old DynamoDB lock table (dynamodb_table) is deprecated. Use use_lockfile. If an interviewer asks, explain what locking prevents (two concurrent applies corrupting state) and that older setups used DynamoDB.

In each env root, backend.tf has an s3 backend block with bucket, key (e.g. staging/terraform.tfstate, production/terraform.tfstate, shared/terraform.tfstate), region, encrypt = true, use_lockfile = true. Backend blocks can't use variables — that's expected; mention partial backend configuration (-backend-config) as an alternative.

Docs: Terraform → Backend Type: s3 page (read the locking section carefully); State: Locking.

Done when: terraform apply in bootstrap creates the bucket; terraform init in an env root successfully uses the S3 backend; you can see the state object in S3 after a first apply.

6.3 modules/network

Resources:

  • data "aws_availability_zones" (state = available).
  • aws_vpc — cidr_block (e.g. 10.10.0.0/16 staging, 10.20.0.0/16 prod — non-overlapping so you could peer later), enable_dns_support = true, enable_dns_hostnames = true (needed for RDS endpoint resolution and VPC endpoints).
  • aws_subnet × 3 tiers × 2 AZs via for_each:
    • public (map_public_ip_on_launch = true) — ALB + NAT only,
    • private-app — ECS tasks,
    • private-db — RDS (separate tier means the DB route table/NACLs can be stricter, and it's the pattern reviewers expect).
  • aws_internet_gateway.
  • aws_eip with domain = "vpc" (the old vpc = true argument no longer exists — a common error from old tutorials).
  • aws_nat_gateway in a public subnet. Variable single_nat_gateway (bool): true for staging (cost), false for prod (one NAT per AZ for AZ-failure resilience). This variable is a great README talking point.
  • aws_route_table + aws_route + aws_route_table_association: public → IGW; private → NAT (per AZ if multiple NATs); db tier can have no internet route at all.
  • VPC Flow Logs (counts as "system/network logs"): aws_flow_log → aws_cloudwatch_log_group (retention 7–14 days) with an aws_iam_role trusted by vpc-flow-logs.amazonaws.com.

Variables: project, environment, vpc_cidr, az_count (default 2), single_nat_gateway, flow_log_retention_days. Outputs: vpc_id, public_subnet_ids, private_app_subnet_ids, private_db_subnet_ids, vpc_cidr.

[Extra] VPC endpoints (aws_vpc_endpoint): an S3 gateway endpoint is free and reduces NAT data charges for ECR image layers (stored in S3). Interface endpoints for ECR/Logs/Secrets Manager remove the need for NAT entirely but cost per hour per AZ — mention the trade-off rather than necessarily building it.

Docs: AWS VPC User Guide → VPC with public and private subnets, NAT gateways, Flow logs. Registry pages for each resource above.

Done when: in the VPC console you can see the subnets, route tables pointing correctly, and a NAT gateway in "Available".

6.4 Security groups

Use the modern per-rule resources aws_vpc_security_group_ingress_rule / aws_vpc_security_group_egress_rule attached to aws_security_group (the registry recommends these over inline ingress {} blocks — mention why: avoids rule conflicts and gives each rule its own ID/tags).

SG Ingress Egress
alb-sg 80 (and 443 if HTTPS) from 0.0.0.0/0 app port to app-sg only
app-sg app port from alb-sg only (referenced_security_group_id) 443 to 0.0.0.0/0 (ECR, Secrets Manager, CloudWatch via NAT) and 5432 to db-sg
db-sg 5432 from app-sg only none needed

Key talking point: rules reference security groups, not CIDRs — so it stays correct as tasks scale and IPs change. Nothing can reach the DB except the app; nothing can reach the app except the ALB.

Docs: AWS VPC → Security group rules; registry pages for the two rule resources.

6.5 envs/shared — ECR and GitHub OIDC

ECR:

  • aws_ecr_repository: image_tag_mutability = "IMMUTABLE" (a tag like a git SHA can never be overwritten — auditability and safe rollbacks), image_scanning_configuration { scan_on_push = true }, encryption configuration, force_delete = true only because this is a demo (say so).
  • aws_ecr_lifecycle_policy: expire untagged images after N days, keep last N (e.g. 20) tagged images — cost control.

GitHub OIDC (no long-lived AWS keys in GitHub — a major security point):

  • aws_iam_openid_connect_provider with url = "https://token.actions.githubusercontent.com" and client_id_list = ["sts.amazonaws.com"]. (Thumbprints are no longer required to be accurate for GitHub's provider in current AWS/provider versions; check the registry page for your provider version.)
  • Two roles: github-deploy-staging and github-deploy-production (or one role with a broader sub for the assignment, noting the improvement). Build the trust policy with data "aws_iam_policy_document":
    • action sts:AssumeRoleWithWebIdentity, principal = the OIDC provider ARN,
    • condition StringEquals on token.actions.githubusercontent.com:aud = sts.amazonaws.com,
    • condition StringLike on token.actions.githubusercontent.com:sub = repo:<owner>/<repo>:environment:staging (and :environment:production for the prod role). Restricting by environment means only a job that passed the production approval gate can assume the production role — excellent interview point.
  • Permissions policy (least privilege): ECR push actions (ecr:GetAuthorizationToken on *, and on the repo ARN: BatchCheckLayerAvailability, InitiateLayerUpload, UploadLayerPart, CompleteLayerUpload, PutImage, BatchGetImage), ECS deploy actions (ecs:DescribeTaskDefinition, ecs:RegisterTaskDefinition, ecs:UpdateService, ecs:DescribeServices), and iam:PassRole limited to the task and execution roles of that environment.

Note: the ECS task/execution roles live in the env roots, so either create the deploy roles in the env roots, or pass role ARNs in. Simplest clean approach: OIDC provider + ECR in shared; each env root creates its own deploy role referencing the provider ARN (look it up with data "aws_iam_openid_connect_provider"). Decide and document.

Outputs: ecr_repository_url, github_oidc_provider_arn (and deploy role ARNs if created here).

Docs: GitHub Docs → Security hardening with OpenID Connect → Configuring OpenID Connect in Amazon Web Services; README of aws-actions/configure-aws-credentials (has a sample trust policy); AWS ECR User Guide → Lifecycle policies, Image tag mutability.

Bootstrap gotcha — the first image: the ECS service needs an image to exist. After applying shared, build and push one image manually (aws ecr get-login-password | docker login ..., docker build, docker tag, docker push) and pass that URI to the env as a variable for the very first apply. Write this in the README setup steps and in your challenges log.

6.6 modules/alb

  • S3 bucket for access logs (aws_s3_bucket + public access block + encryption SSE-S3 — ALB access logs don't support SSE-KMS customer keys, a classic gotcha — + lifecycle expiration e.g. 30 days + aws_s3_bucket_policy that allows Elastic Load Balancing to write). The exact principal differs by region (older regions like ap-south-1 use a regional ELB account ID); copy it from the AWS doc page Enable access logs for your Application Load Balancer. If the policy is wrong, terraform apply of the ALB fails with an "Access Denied for bucket" error — expect it, log it.
  • aws_lb: load_balancer_type = "application", internal = false, public subnets, alb-sg, drop_invalid_header_fields = true (security), access_logs { bucket, enabled = true, prefix }, enable_deletion_protection = variable (true in prod).
  • aws_lb_target_group: target_type = "ip" (mandatory for Fargate/awsvpc — the default instance will fail), port = app port, protocol = "HTTP", vpc_id, health_check { path = "/health", matcher = "200", interval, healthy_threshold, unhealthy_threshold }, deregistration_delay = 30 (faster deploys than the 300s default — explain why).
  • aws_lb_listener on 80: default_action forward to target group.
  • [Extra] HTTPS: only if you own a domain — aws_acm_certificate (DNS validation) + aws_route53_record + aws_acm_certificate_validation, a 443 listener with a modern ssl_policy, and the 80 listener changed to a redirect to 443. If you don't have a domain, state clearly in the README: "Production would terminate TLS at the ALB with ACM; omitted because no domain was available for the demo." That's an acceptable, honest trade-off.
  • [Extra] aws_wafv2_web_acl with AWS managed rule groups associated to the ALB.

Outputs: alb_dns_name, alb_arn_suffix, target_group_arn, target_group_arn_suffix (the arn_suffix values are what CloudWatch metric dimensions need — you'll use them in dashboards).

Docs: ELB User Guide for ALBs → Target groups → Health checks, Access logs; registry aws_lb, aws_lb_target_group, aws_lb_listener.

6.7 modules/rds

  • aws_db_subnet_group with the two private-db subnets (RDS requires subnets in at least two AZs even for single-AZ instances).
  • aws_db_parameter_group (family must match the major version, e.g. postgres16): log_min_duration_statement (e.g. 500 ms — log slow queries), log_connections/log_disconnections [Extra], ensure rds.force_ssl = 1 (encryption in transit).
  • aws_db_instance — the arguments that matter and why:
Argument Value Why

instance_class db.t4g.micro Graviton, cheapest
allocated_storage / max_allocated_storage 20 / 50 Storage autoscaling prevents disk-full outages
storage_type gp3 Cheaper baseline IOPS than gp2

publicly_accessible false

backup_retention_period var: 1–3 staging / 7–14 prod PITR window — your backup deliverable

Outputs: db_endpoint, db_address, db_port, db_name, db_instance_identifier, and master_user_secret[0].secret_arn (the ARN of the generated secret — the ECS module needs it).

Important rotation gotcha (great interview point): an RDS-managed secret is rotated automatically (default every 7 days). ECS injects secrets only at task start, so running tasks keep the old password and will fail on new connections after rotation. Mitigations to document: trigger a new ECS deployment on rotation (EventBridge rule on the Secrets Manager rotation event), or have the app fetch the secret at connect time with caching, or rely on connection retry + task restart. You don't have to build it — just show you know.

Docs: RDS User Guide → Password management with Amazon RDS and AWS Secrets Manager, Backing up and restoring, Working with parameter groups, Publishing PostgreSQL logs to CloudWatch Logs; registry aws_db_instance (read the master_user_secret attribute section).

Done when: RDS shows "Available"; the secret appears in Secrets Manager; the instance has no public endpoint.

6.8 modules/ecs

  • aws_ecs_cluster with setting { name = "containerInsights", value = "enabled" } (or "enhanced" — the newer enhanced observability tier with more granular metrics; check pricing). Container Insights is what gives you CPU/memory/storage/network metrics per service and task.
  • aws_ecs_cluster_capacity_providers with FARGATE and FARGATE_SPOT. Staging can run 100% Spot (cost); prod uses on-demand base + optional Spot. Great cost talking point.
  • aws_cloudwatch_log_group /ecs/<name_prefix> with retention_in_days (never leave infinite retention — a hidden cost).
  • Two IAM roles — know the difference cold, it's asked constantly:
    • Execution role (used by the ECS agent before/around your container): pulls the image from ECR, writes logs, reads the secret. Attach the AWS managed policy AmazonECSTaskExecutionRolePolicy plus an inline policy allowing secretsmanager:GetSecretValue on the RDS secret ARN only (and kms:Decrypt if the secret uses a customer-managed key).
    • Task role (used by your application code at runtime): grant only what the app calls — likely nothing for this app. Leave it minimal and say so.
    • Both trusted by ecs-tasks.amazonaws.com.
  • aws_ecs_task_definition: family, network_mode = "awsvpc", requires_compatibilities = ["FARGATE"], cpu = 256, memory = 512, runtime_platform (OS + CPU architecture), execution_role_arn, task_role_arn, and container_definitions = jsonencode([...]) with:
    • name, image (variable), essential = true, portMappings (containerPort = app port),
    • environment: DB_HOST, DB_PORT, DB_NAME, PORT, ENVIRONMENT,
    • secrets: DB_USER and DB_PASSWORD with valueFrom set to the secret ARN plus a JSON-key suffix (the format <secret-arn>:<json-key>:: — the RDS-managed secret JSON has username and password keys). Read the AWS doc for the exact syntax; getting it wrong produces a ResourceInitializationError at task start.
    • logConfiguration with logDriver = "awslogs" and options awslogs-group, awslogs-region, awslogs-stream-prefix,
    • [Extra] readonlyRootFilesystem = true (add a writable tmp volume if your server needs one), user non-root, linuxParameters { initProcessEnabled = true }.
  • aws_ecs_service:
    • cluster, task_definition, desired_count = 2 (one per AZ),
    • capacity_provider_strategy (or launch_type = "FARGATE"),
    • network_configuration { subnets = private-app, security_groups = [app-sg], assign_public_ip = false },
    • load_balancer { target_group_arn, container_name, container_port },
    • health_check_grace_period_seconds (e.g. 60, gives the app time to boot),
    • deployment_minimum_healthy_percent = 100, deployment_maximum_percent = 200 (zero-downtime rolling deploys),
    • deployment_circuit_breaker { enable = true, rollback = true } — automatic rollback if new tasks fail health checks. Big differentiator; demo it in the video if time permits by deploying a deliberately broken image.
    • lifecycle { ignore_changes = [task_definition, desired_count] } — critical: after this, the CI/CD pipeline owns which task definition revision runs, and autoscaling owns the count. Without this, every terraform apply would roll the service back to the Terraform-known image. Explain this division of ownership in the README.
    • depends_on the ALB listener (the target group must be attached to a listener before the service registers).
    • [Extra] enable_execute_command = true (ECS Exec for debugging, requires SSM permissions on the task role) — note security implications.
  • Autoscaling: aws_appautoscaling_target (service namespace ecs, scalable dimension ecs:service:DesiredCount, min 2 / max 4) + aws_appautoscaling_policy with TargetTrackingScaling on ECSServiceAverageCPUUtilization (target ~60%). [Extra] a second policy on ALBRequestCountPerTarget.

Outputs: cluster_name, service_name, task_definition_family, log_group_name, task_execution_role_arn, task_role_arn.

Docs: ECS Developer Guide → Task definition parameters, Pass Secrets Manager secrets through Amazon ECS environment variables, Task execution IAM role, Task IAM role, Deployment circuit breaker, Service auto scaling, Amazon ECS Container Insights metrics; registry pages for each resource.

7.2 ci.yml — runs on every PR

Trigger: on: pull_request targeting main. Top-level permissions: contents: read (least privilege — default token permissions are broader than needed). Add a concurrency group keyed on the PR so new pushes cancel stale runs.

Jobs (run in parallel where independent):

  1. lint
    • checkout (actions/checkout), setup language (actions/setup-python with pip cache),
    • code linter (ruff/flake8 or eslint),
    • Dockerfile lint (hadolint/hadolint-action),
    • Terraform: hashicorp/setup-terraform, terraform fmt -check -recursive, and for each root terraform init -backend=false + terraform validate,
    • [Extra] tflint, Checkov (bridgecrewio/checkov-action) for IaC misconfigurations — triage findings; suppress any you intentionally accept with a comment explaining why (e.g. "no HTTPS: no domain for demo").
  2. unit-tests — install deps, run unit-marked tests with coverage; upload the coverage report as an artifact (actions/upload-artifact).
  3. integration-tests — job-level services: block with a postgres:16 container (env: user/password/db; options with --health-cmd pg_isready and health intervals; ports: 5432:5432); job env sets DB_HOST=localhost etc.; run integration-marked tests.
  4. security-scan
    • dependency scan: pip-audit / npm audit --audit-level=high, or Trivy filesystem mode,
    • build the image without pushing (docker/setup-buildx-action + docker/build-push-action with load: true, push: false), with GitHub Actions cache (cache-from/to: type=gha) [Extra],
    • container scan with aquasecurity/trivy-action on the built image, severity: CRITICAL,HIGH, exit-code: 1, ignore-unfixed: true (don't fail on CVEs with no fix available — explain this pragmatic choice),
    • [Extra] output SARIF and upload with github/codeql-action/upload-sarif (needs security-events: write) so findings show in the Security tab,
    • [Extra] secret scanning with gitleaks.
  5. notify-on-failure — needs: [lint, unit-tests, integration-tests, security-scan], if: failure(), posts to Slack using slackapi/slack-github-action with the webhook secret. Include repo, workflow name, branch/PR, actor, and a link to the run (github.server_url/github.repository/github.run_id context values). Email alternative: an SMTP action such as dawidd6/action-send-mail.

[Extra] terraform-plan job on PRs that change infra/** (paths filter), using a read-only OIDC role, posting the plan as a PR comment. Shows mature IaC workflow.

Docs: GitHub Docs → Workflow syntax for GitHub Actions (on, jobs, needs, if, permissions, concurrency, environment, outputs), About service containers → Creating PostgreSQL service containers, Expressions → Status check functions (failure(), always()), Contexts; READMEs of each action listed (they're the real docs — read the inputs table).

7.3 cd.yml — runs on merge to main

Trigger: on: push to main (plus workflow_dispatch for manual reruns). permissions: id-token: write, contents: read (id-token is required for OIDC). concurrency: deploy-${{ github.ref }} with cancel-in-progress: false (never cancel a deploy halfway).

[Extra, recommended] Put the CI jobs in a reusable workflow (on: workflow_call) and call it from both ci.yml and cd.yml, so the exact same tests gate deploys — DRY and a strong design point.

Jobs:

  1. test — call the reusable CI workflow (or rerun unit/integration tests).
  2. build-and-push (needs: test)
    • aws-actions/configure-aws-credentials with role-to-assume and aws-region (OIDC),
    • aws-actions/amazon-ecr-login,
    • build image tagged with ${{ github.sha }} (immutable, traceable to a commit — never deploy latest),
    • Trivy scan the image before pushing; fail on critical/high,
    • push; expose the full image URI as a job output for later jobs.
  3. deploy-staging (needs: build-and-push, environment: { name: staging, url: <APP_URL var> })
    • configure AWS creds with the staging role,
    • fetch the current task definition (aws ecs describe-task-definition --task-definition <family> --query taskDefinition > task-def.json),
    • aws-actions/amazon-ecs-render-task-definition to swap in the new image URI,
    • aws-actions/amazon-ecs-deploy-task-definition with wait-for-service-stability: true (job fails if the rollout fails; the circuit breaker rolls back),
    • run scripts/smoke-test.sh <APP_URL> (bash: curl /health and /ready with retries and a timeout; non-zero exit on failure).
  4. deploy-production (needs: [build-and-push, deploy-staging], environment: production)
    • the job pauses here until you approve in the GitHub UI — that's requirement 2.1's manual approval,
    • identical steps with prod variables and the same image URI from build-and-push (build once, promote — never rebuild for prod),
    • smoke test prod.
  5. notify — on failure (if: failure()), Slack message; [Extra] also notify success of production deploys with the commit SHA and approver.

Why fetch the task definition from AWS instead of keeping a JSON file in the repo? Because Terraform owns the task definition shape (env vars, secrets, roles); the pipeline only changes the image. This avoids two sources of truth. Explain this in the README — interviewers love seeing that you thought about Terraform vs pipeline ownership.

Rollback story (write it in docs/runbook.md): (a) automatic — circuit breaker; (b) manual — rerun cd.yml deploy jobs for an earlier commit via workflow_dispatch with an image-tag input [Extra], or aws ecs update-service --task-definition <previous-revision>. Immutable SHA tags make every previous version available.

Docs: README of aws-actions/configure-aws-credentials, aws-actions/amazon-ecr-login, aws-actions/amazon-ecs-render-task-definition, aws-actions/amazon-ecs-deploy-task-definition; GitHub Docs → Deploying to Amazon Elastic Container Service (official guide — your primary reference for this file), Reusing workflows, Defining outputs for jobs; slackapi/slack-github-action README (incoming-webhook technique); Slack docs → Sending messages using incoming webhooks.

Done when: a PR shows all CI checks green (and you've seen one fail and notify Slack — deliberately break a test once and screenshot the Slack message); merging deploys to staging automatically; production waits for approval; after approval prod updates; both smoke tests pass.

8.4 Centralised logging — the three required categories

Category What Where How (Terraform)
Application logs JSON stdout from containers CloudWatch Logs /ecs/<prefix> awslogs driver in task def; log group with retention
Access logs Every HTTP request at the edge S3 bucket (ALB access logs) + app-level request logs in CloudWatch access_logs on aws_lb; [Extra] Athena table to query them
System logs Network flows, platform events, DB engine logs CloudWatch Logs VPC Flow Logs (aws_flow_log); ECS task/service/deployment events via EventBridge (aws_cloudwatch_event_rule with source = ["aws.ecs"] → aws_cloudwatch_event_target → a log group, plus aws_cloudwatch_log_resource_policy allowing events.amazonaws.com to write); RDS postgresql log export; [Extra] CloudTrail for API audit logs

Explain the Fargate "system logs" nuance in the README (this is where you show maturity): on Fargate there is no host OS you manage, so traditional syslog/journald doesn't exist for you to collect — AWS operates that layer. The system-level signals that are yours — network flows, container lifecycle events (OOM kills, failed health checks, stopped tasks with reasons), database engine logs, and API audit — are all centralised. If OS-level logs are required, the EC2-based alternative would run the CloudWatch agent shipping /var/log/messages/journald. [Extra] If you want to show this concretely, add a tiny EC2 instance (e.g. a bastion accessed only via SSM Session Manager — no SSH port open) with the CloudWatch agent installed via user_data.

Saved queries: aws_cloudwatch_query_definition for "errors in last hour", "slowest requests (p95 by path)", "requests by status code". Example of what they do: filter JSON logs where level = "ERROR", stats count() by bin(5m). Docs: CloudWatch Logs → CloudWatch Logs Insights query syntax.

Retention on every log group (7 days staging, 30 prod) — cost and compliance talking point.

Why CloudWatch and not ELK/Loki? Zero infrastructure to run, native integration, pay-per-use; a self-hosted ELK or OpenSearch cluster would cost more than the entire app for this scale. Mention OpenSearch/Loki or Datadog as options at higher scale or for multi-cloud.

Docs: CloudWatch User Guide → Using Amazon CloudWatch dashboards (and Dashboard Body Structure and Syntax in the API reference), Using metric math, Alarms; ECS → Container Insights metrics; ALB → CloudWatch metrics for your Application Load Balancer; RDS → Metrics reference for Amazon RDS; EventBridge → Amazon ECS events.

  • Workspaces vs separate roots vs separate accounts.
  • Task execution role vs task role.

  • Security group vs NACL; why private subnets; why a separate DB subnet tier.
  • How does the ALB decide a target is healthy; what's deregistration delay; how do you get zero downtime?
  • How would you do blue/green or canary? (ECS + CodeDeploy, weighted target groups, or ECS native blue/green.)
  • How would you run DB migrations safely? (expand/contract pattern, migration task before deploy.)
  • Why p95/p99 and not average latency? What alerts would page someone at 3 a.m. vs create a ticket?
  • How would you reduce this setup's cost by 50%? (NAT is often the surprise.)
  • Your biggest challenge in this assignment and how you debugged it.
  • Live tasks to rehearse: add a new env var to the app end-to-end; add an alarm; scale the service; roll back to a previous revision; read a failed task's stopped reason; write a Logs Insights query on the spot.
